## Implemented scope

- Operator-only `all_tcp_ports`, mutually exclusive with explicit ports and
  independent of ping. Both D-21 ranges, ports 1/65535, invalid zero, private
  neighbors, network/broadcast, mapped answers and unconditional metadata denials
  are covered. Grants are not automatically enabled.
- HTTP/HTTPS GET, TCP connect/close and native Windows/Linux IPv4/IPv6 ping.
  Resolve once under a shared total deadline, reject whole answer sets over eight,
  authorize every member before family selection, and use only numeric capability
  addresses. Auto attempts at most two addresses sequentially with split remaining
  time. Original Host/path/query/TLS name are preserved. No redirect following,
  proxy inheritance, automatic retry, decompression, cookie jar, body download or
  connection pool. Hyper enforces 32 KiB wire headers/buffer strategy and 100
  headers; exact boundary and oversized shapes pass controlled HTTP/HTTPS tests.
- Mandatory rustls verification, public roots plus bounded optional operator DER
  files. Trusted, untrusted, wrong-name and expired certificates are tested.
  Ping validates source/correlation/payload; Linux uses datagram ICMP only,
  Windows uses isolated documented synchronous FFI with aligned owned buffers.
  Permission/unavailable support produces a local fault, not target down.
- Four admitted probes, one active probe per monitor, no queued network work.
  Native DNS/ICMP retains admission after timeout/cancellation until it ends.
  Six blocking helpers cover four native calls, one hash and storage shutdown;
  two async workers and the existing 128-command SQLite worker remain bounded.
- Persisted normal/confirmation scheduling and next due time. Below threshold,
  a completed failure replaces the regular check with completion plus 30 seconds.
  Success, confirmed down or a local fault resumes cadence from the last due slot.
  Missed confirmations reset the streak and reconstruct normal unknown slots,
  never hypothetical further confirmations. Initial/restart due times use bounded
  jitter. Wall/monotonic drift over two seconds records a discontinuity/reanchor.
- Revisions and schedule generations discard stale/duplicate results. Edits and
  pause end incidents with explicit reasons; restart keeps an unresolved incident
  with an observation-gap flag. System errors are stored separately from target
  evidence. No stale or unsaved computed success becomes a durable status.
- Results, state, schedule cursor, hourly counts, incidents and enabled compact
  outbox transitions commit in one transaction. Logical down/recovery events are
  unique. Pending outbox overflow retains jobs/incidents and increments a durable
  suppression counter. Sending/digests/retries/settings remain WP-04.
- Exact sample availability and separate expected-slot coverage, N/A for empty
  denominators, pause exclusion, unknown outage/local-fault slots, immediate
  idempotent aggregation. Recent windows clip raw slots exactly; older windows
  sum hourly counts and label partial boundaries/discontinuities.
- Seven-day raw, 90-day hourly and 180-day closed-incident retention; open incidents
  survive. No incident row cap. Cleanup/tombstones delete at most 500 history rows
  per command. SQLite page/WAL/free-space admission is preserved. Fixed counters
  enforce raw/hourly/epoch bounds; pressure rolls back writes rather than
  shortening retention. Duplicate handling targets only the unique slot key, so
  it cannot suppress capacity constraints in counter triggers.
- Protected JSON summary/create/edit/pause/resume/delete/history/incidents APIs
  reuse account authentication, canonical Host/Origin, CSRF and mutation limits.
  Create retry keys are admin-scoped, digest/operation checked and bounded to
  100/24 hours. Delete requires explicit history confirmation. History is limited
  to retained 90-day windows/300 points, incidents to 100 rows, responses to
  256 KiB. Malformed input/path/query errors return safe bounded categories.
  Readiness additionally checks scheduler progress. Full HTML/GUI remains WP-05.

## Decisions and contract reconciliation

[D-23](../../decisions.md#d-23-wp-03-implementation-baseline-2026-10-12) records
implementation details. The proposed hourly ceiling increases by **50 rows**,
from 108,000 to 108,050, because a rolling 90-day window intersects a partial
boundary hour for each of 50 monitors. Whole-hour expiration preserves that
boundary. This preserves confirmed 90-day retention, 180-day incidents without
a row cap, the 256 MiB incremental RAM envelope and firm 2 GiB disk limit.
No confirmed requirement was weakened.

Migration 2 preserves any preconfigured foundation monitors and starts their
coverage at migration time: WP-01/02 had no monitoring scheduler from which to
infer earlier enabled slots. Imported foundation results use generation zero;
new results have an epoch-aware unique key. Upgrade preflight and the supported
`pre-migration.db` snapshot are unchanged; existing recovery points are not
overwritten. Architecture, data model, security, web/API, decision register and
scoped acceptance were updated together.

## Review corrections (2026-10-13)

The owner assigned only the corrections in WP03-R1/R2. No later package,

**WP03-R1 (R-05/F-05/F-09; V-04/V-05):** the scheduler now admits a separate
`Maintain` transaction before every pending restart or clock-jump reanchor
attempt. Incomplete/error catch-up cannot skip housekeeping. Each cleanup still
deletes at most 500 history rows and uses the existing disk/WAL/free-space gates,
row ceilings and age windows. Recovery stays degraded until it commits; pressure
without eligible data still blocks probes. Epoch reference checks use the
existing monitor/epoch index. Open incidents, young closed incidents, D-19
cadence and unknown coverage remain protected.

The five tests in [review_regressions.rs](../../../tests/review_regressions.rs)
exercise real storage and scheduler/probe paths on controlled loopback targets:

- Restart at exactly 1,010,000 actual raw rows with trigger-maintained counters:
  cleanup removes 500 expired rows, four missed slots commit as unknown, leaving
  1,009,504 rows before probes resume. No fixture counter override is used.
- Restart at exactly 10,000 actual epochs reclaims 500 expired epochs and commits
  a new one; open and young closed incidents survive, the old open incident gains
  an observation-gap flag, and a real successful HTTP probe recovers the target.
- At 10,000 young, non-reclaimable epochs, recovery stays visibly degraded,
  performs no probe, preserves the quota/young rows and rolls back missed slots.
- A running scheduler with independent wall/monotonic clocks crosses epoch
  expiry on a clock jump, cleans up, commits a `clock_jump` epoch and resumes TCP.
- Delete/cleanup/restart/recreate with a retained create key cannot resolve the
  former identity to a replacement; stale edit/delete leave the replacement
  at its original name/revision.

**WP03-R2 (R-05/F-03/F-09; V-04/API contract):**
[migration 3](../../../migrations/0003_monitor_identity.sql) adds a durable,
single-row decreasing allocator. Legacy service IDs were positive implicit
SQLite rowids; newly allocated IDs are negative signed integers. This disjoint
range protects even deleted legacy IDs whose historical maximum has already
disappeared. A sequence initialized from the live maximum alone, or adding
AUTOINCREMENT after deletion, cannot reconstruct that missing history; see
[SQLite rowid allocation](https://www.sqlite.org/autoinc.html). Existing IDs and
foreign keys remain intact. Allocation and monitor creation commit together,
deletion/cleanup never resets the sequence, exhaustion fails closed, and startup
validates the allocator. IDs remain opaque signed integers in the unchanged API
request shape. The 100-key/24-hour limit is unchanged. Replaying a deleted create
returns conflict (409), stale mutations return not found (404), and B remains
unchanged. A separate version-2 upgrade test preserves a live legacy ID and its
epoch, protects a retained deleted-ID reference, verifies the supported migration
snapshot and verifies decreasing allocation after another restart.

An existing rollback test selected the first sorted monitor and inadvertently
selected its paused fixture once IDs became negative. It now explicitly selects
the enabled fixture and still asserts rollback. The controlled HTTP server also
checks the read result, resolving a warning-denied clippy failure. Neither change
weakens the behavior being verified.
