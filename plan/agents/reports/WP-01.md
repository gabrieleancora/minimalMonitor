## Implemented scope and decisions

- Root Rust application/library, pinned toolchain, committed lockfile, modular
  config/bounds/error/ownership/storage/web boundaries and build/operator notes.
- Strict 16 KiB TOML configuration with explicit development/production modes,
  loopback-only listen addresses, production HTTPS origin validation, unknown-field
  rejection and configuration-relative paths. Errors emit safe categories only.
  Configuration-only validation performs no state mutation.
- Persistent exclusive OS lock in the private state directory. `Storage::start`
  consumes its ownership guard, preventing a second worker from reusing it. The
  dedicated thread retains the lock through database close, including cancellation
  or an async shutdown timeout. Lock files are never unlinked. Future local
  bootstrap/reset must acquire the same guard with the service stopped.
- Two async workers, at most two blocking helpers, one SQLite worker and a bounded
  128-command channel. Nonwaiting queue/semaphore admission returns explicit
  busy/unavailable errors. Shared permits reserve four probes, one password hash
  and one sender without implementing those later operations. Commands expire;
  canceled callers skip work; worker drop stops admission despite surviving
  client clones. SQL progress cancellation is independent of the async wait.
- Migration 1 defines all 14 planned entities, indexes, FK/field/uniqueness
  constraints, singletons and session/monitor caps. No admin, credentials,
  monitors, samples or incidents are seeded. No feature mutation API is exposed.
  History does not cascade on monitor deletion; later workers must perform the
  specified bounded cleanup and atomic transitions.
- Application identity/schema validation before journal changes, migration/version
  transactions, initial-schema idempotency and rejection of foreign/inconsistent/
  newer schemas before binding. Failed DDL/data migration rolls back its version.
  Initial empty schema needs no recovery snapshot; the upgrade path preflights
  worst-case growth and takes a supported incremental SQLite snapshot before any
  later migration. Existing snapshot files block replacement. Snapshot consistency
  and refusal to overwrite are tested; no actual version-2 upgrade exists yet.
- SQLite WAL/FULL/FK enforcement, 2 MiB cache target, two-second busy timeout,
  defensive mode, SQL/value/column/bind/attachment limits and a page-size-derived
  main ceiling of at most 512 MiB. Checkpoints and bounded directory/free-space
  accounting feed write-admission health. WAL at 32 MiB or free space below
  128 MiB prevents admission; 32 MiB is not misrepresented as a hard WAL limit.
  Migration preflight preserves the firm 2 GiB allocation, including one snapshot
  and the binary/log/headroom reserve. Later writes must check admission inside
  the worker; this foundation has no history/outbox/configuration mutation methods.
- HTTP/1 loopback listener with 16 active-connection permits covering parsing,
  handling and writes, 16 KiB header/body bounds, 100-header ceiling, five-second
  connection lifetime and no keep-alive. Excess sockets close without queued
  tasks. Only local `/health/live` and `/health/ready` exist. Readiness performs
  a fresh worker round-trip and fails safely on unavailable storage/admission.
  Responses have bounded safe codes/messages/request IDs and restrictive headers.
  Socket peer identity is authoritative; forwarded headers cannot grant access.
  A local proxy is itself local, so WP-06 must exclude health routes publicly.
- Ctrl+C handler and Linux SIGTERM handler, bounded connection drain, worker
  shutdown/checkpoint/close and safe nonzero startup failures. Linux graceful
  termination was executed; Windows graceful console termination was not.

D-16 records routine implementation choices. Axum 0.8.9, Tokio 1.53.2, Hyper
1.12.0 and hyper-util 0.1.21 preserve the chosen stack. rusqlite 0.40.2 /
libsqlite3-sys 0.38.2 bundle **SQLite 3.53.2**, updating the feasibility prototype's
older SQLite after review of [SQLite's security notes](https://www.sqlite.org/cves.html).
fs2 0.4.3 supplies Windows/Linux OS locking and free-space accounting. TOML 1.1.4,
serde 1.0.229, URL 2.5.8 and Tower 0.5.3 provide bounded configuration/HTTP support;
tempfile 3.27.0 is test-only. Exact transitive versions are in the root lockfile.
There is no Node runtime, external database, container daemon, probe transport,
password implementation or Telegram client in this package.

## Owner review fixes: WAL recovery and shared lock (2026-10-10)

The owner requested two follow-ups before WP-01 sign-off. P2 exposed a real
recovery bug: PASSIVE can checkpoint every frame while leaving a WAL file
allocated at or above 32 MiB. Maintenance now makes at most one SQLite TRUNCATE
attempt at that threshold with the busy timeout temporarily zero, retaining the
existing command deadline and restoring the ordinary two-second timeout even
on SQL failure. It then remeasures all admission inputs. A pinned reader/writer
keeps admission blocked; later maintenance/readiness retries safely after it
finishes. No manual WAL deletion, retry loop, new dependency or relaxed bound
was introduced. This follows [SQLite checkpoint semantics](https://www.sqlite.org/pragma.html#pragma_wal_checkpoint).

The new [integration test](../../../tests/wal_recovery.rs) uses the actual running
worker/client and controlled SQLite fixture connections. A held read transaction
and 72 bounded 512 KiB payload updates create a real WAL above the threshold.
Three health checks remain blocked while the reader is pinned and its old
snapshot stays intact. Releasing the reader lets the same worker/client reclaim
the file and resume write admission without restart. Committed revision 72,
a subsequent fixture write and database integrity are verified. WP-01 has no
feature mutation API yet: this proves worker admission/reclamation, not future
account/session transaction guards, which must be enforced inside the worker.

Regression sensitivity was checked on Windows: temporarily removing only the
recovery block caused `cargo test --locked --offline --test wal_recovery` to fail
at resumed admission (exit 101); restoring the fix passed. The full Windows
runner and actual Fedora runner then passed all six checks on the final source.
Existing evidence was archived before reruns; remote source bytes were compared
against the prior transfer before updates and against the tested archive after.
No toolchain, dependency graph, shared Linux policy or production service changed.

P3 reconciles [deployment](../../operations/deployment.md) with implemented
persistent `state_dir/owner.lock`. Service, bootstrap/reset and offline database
commands must use that same exclusive lock through database close. Preserve the
lock inode and state directory during restore; no runtime-directory alternative
or unlink at startup/shutdown is allowed. No bootstrap/reset command was added.
