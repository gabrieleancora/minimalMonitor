## Implemented scope

- `admin-bootstrap` and `admin-reset` acquire the existing persistent state lock
  before prompting and hold it through database shutdown. No default admin,
  public setup, registration, password argument or environment credential input.
  Commands require an interactive terminal, hide input, confirm the new password,
  refuse duplicate bootstrap/absent-account reset, and use the dedicated SQLite
  worker. Reset atomically replaces credentials, increments generation, revokes
  all sessions and records bounded nonsensitive audit metadata.
- Argon2id v19 uses 19456 KiB, two iterations, one lane, random 16-byte salts and
  32-byte output. Verification checks stored parameters before allocating work.
  One nonwaiting shared permit covers each blocking hash task until it ends,
  including caller cancellation. Unknown-user logins perform equivalent hashing;
  username/password failures use the same safe error. Passwords and signing keys
  use zeroizing ownership; secret types deliberately lack Debug/Display.
- Fresh random 256-bit opaque session tokens; SQLite stores only their SHA-256.
  Separate random CSRF bindings, signed five-minute stateless preauth tokens,
  constant-time comparisons, canonical Origin, cookie flags and session rotation.
  Production uses Secure `__Host-` cookies; explicit loopback HTTP development
  uses separate names. Idle/absolute expiry, oldest eviction at five sessions,
  logout, password change/current-password verification, reset and restart
  persistence are implemented. The proposed batched activity contract is made
  explicit: checkpoint timestamps may conservatively expire a session up to one
  minute early. Clock rollback fails closed; expiry is never extended beyond
  24 hours. This does not relax the confirmed login/privacy requirement.
- Account/session commands share the foundation's bounded 128-command queue and
  execution/reply deadlines. Every mutation checks storage admission on the
  worker before a short transaction. Login and password change recheck the
  credential generation; change rechecks its session at commit time. Stale
  in-flight verification cannot restore access after reset/change. Success audit
  rows are capped at 5000/30 days; denied requests increment a bounded in-memory
  counter without per-request persistent logging. Healthy idle maintenance
  removes expired session rows; poll activity writes occur at most once/minute.
- Central authorization covers every private path/method, including unimplemented
  feature paths and unknown APIs. Browser GETs redirect; anonymous APIs return
  401. Minimal `/login` form/local script, login/logout, private account-session
  CSRF read and password change exist. Authenticated future features return safe
  501 responses; no monitor data is fabricated. Full GUI remains WP-05.
- Canonical Host/Origin, strict JSON fields, 1024-byte credential bodies,
  foundation 16 KiB general body/header budgets, five-second connection/request
  deadline, 16 admitted connections, bounded fixed responses, no-store/no-sniff,
  restrictive CSP and no-referrer. Bodies are bounded even for routes that do
  not extract JSON. Absolute-form targets are refused. Safe extractor errors
  never reflect credentials, SQL, filesystem paths or submitted markup.
- Five-attempt/minute IP buckets with burst five; a global six/minute hash-start
  bucket with burst two shared by login/password change; 2048 IP-entry cap/expiry;
  authenticated mutation admission at 30/minute. Excess receives 429/503 and retry
  hints. No permanent username lockout or unbounded waiting hash queue.
- Optional configured loopback proxy peer may supply exactly one numeric
  `X-Real-IP`; other peers use socket identity. All `X-Forwarded-*` values are
  ignored as authority. Missing/malformed/duplicate trusted identity is rejected.
  Without the option, all identity headers are ignored, conservatively grouping
  proxied traffic by socket IP. Health always uses socket locality alone;
  WP-06 must exclude it from public Nginx routes and overwrite trusted identity.
- Shared target parser/operator destination policy, at most 64 CIDR/optional-host
  grants and 64 ports per grant, separate ping permission. Private v4/v6 requires
  an explicit grant; loopback additionally requires /32 or /128. Hard denials
  include metadata/link-local, unspecified, multicast/broadcast, documentation
  and transition/special-use ranges. Mapped addresses are normalized; mapped
  CIDRs, ambiguous hosts, userinfo/fragments/control characters are refused.
  The helper's defensive ceiling is 32 supplied addresses, with literal/answer
  matching. Monitor transports retain eight as their whole-resolution limit.
  The resulting capability retains only validated numeric addresses/ports and
  the normalized original TLS hostname. No browser route can widen grants.

## Owner review: IPv6 metadata denial and DNS limits

The owner returned a P2 security finding and DNS-limit discrepancy to WP-02.
The IPv6 classifier previously treated AWS's `fd00:ec2::254` endpoint as
grantable ULA. It now returns Forbidden for that exact numeric address before
ULA classification or any grant evaluation, preserving unconditional metadata
denial. [AWS documents this IPv6 metadata address](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instancedata-data-retrieval.html).

The new `aws_ipv6_metadata_is_denied_before_any_grant` regression first failed
on the old classifier under `fd00::/8` (Windows targeted test exit 101), then
passed with the fix. It covers literal HTTP/HTTPS/TCP/ping, expanded/case-varied
IPv6 spelling, hostname DNS answers, mixed public/ULA and metadata answers in
both orders, fd00::/8, fc00::/7, ::/0, an exact /128 grant and a matching hostname
grant. Ordinary neighboring ULA remains permitted under appropriate broad grants.
These are pure policy tests; no metadata endpoint or external target was contacted.

The monitoring contract's eight-answer transport limit is preserved. The shared
helper's 32-address ceiling is a separate defensive capacity, not permission to
increase DNS results for monitor transports. WP-03 must reject the whole result
over eight, with no truncation or allowed-subset filtering, then validate every
accepted answer before family selection. Architecture, monitoring, security,
README, D-17 and acceptance were reconciled. The WP-03 dependency now explicitly
requires resolving incident overflow within the firm disk budget while preserving
confirmed 180-day retention before implementation. No overflow behavior or
transport code was implemented and WP-03 remains unassigned/unstarted.
